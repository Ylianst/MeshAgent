Manages parent-child process isolation using named pipe IPC on Windows, allowing a parent process to spawn a sandboxed child process and communicate with it via length-prefixed JSON messages.

## Key Components

- **`create(options)`** — Parent-side factory that spins up a named pipe IPC server, spawns a child process (optionally as a different Windows user via Win-Tasks or SCHTASKS), and returns an EventEmitter-based handle with `ready`, `message`, and `exit` events.
- **`connect(ipcNumber)`** — Child-side entry point that connects back to the parent's named pipe, then listens for `addModule`, `launch`, `message`, and `exit` commands.
- **IPC Transport** — All messages are framed with a 4-byte little-endian length prefix followed by JSON payload, transmitted over a Windows named pipe (`\\.\pipe\taskRedirection-<id>`).

## Usage Example

```javascript
// --- Parent process ---
var childContainer = require('child-container');

var handle = childContainer.create({
  modules: [
    { name: 'my-module', script: '...' }
  ],
  launch: {
    module: 'my-module',
    method: 'start',
    args: ['arg1']
  },
  // Optional: run as a specific Windows user
  user: 'DOMAIN\\username'
});

handle.on('ready', function () {
  console.log('Child is ready');
  handle.message({ hello: 'world' });
});

handle.on('message', function (msg) {
  console.log('Received from child:', msg);
});

handle.on('exit', function (code) {
  console.log('Child exited with code:', code);
});

// --- Child process (auto-invoked via -b64exec bootstrap) ---
// require('child-container').connect('<ipcNumber>') is called automatically
```

## Notes

- Pipe names are randomized (1000–9999) to avoid collisions; use `options._debugIPC` with `options._ipcInteger` to pin the port for debugging.
- On Windows, user-switching falls back from `win-tasks` → SCHTASKS if the first method throws.
- Non-Windows or same-user spawns use `child_process.execFile` with optional `uid` and SpawnTypes support.
