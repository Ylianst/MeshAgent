# How the Windows libjpeg-turbo libraries were built

The options and headers are the ones in `../README.md`. The Windows libraries are built from the git tag `3.2.1`
(`7b499378`) instead of the tarball, and with MSVC flags where that file names gcc and clang ones.

Tools: CMake 4.3.1 with the generator "Visual Studio 18 2026", NASM 3.02.

```bat
cmake -S libjpeg-turbo -B build\<target> -G "Visual Studio 18 2026" -A <platform> -T <toolset> ^
  -DENABLE_SHARED=0 -DWITH_TURBOJPEG=0 -DREQUIRE_SIMD=1 -DWITH_ARITH_ENC=0 -DWITH_ARITH_DEC=0 -DWITH_TOOLS=0 -DWITH_TESTS=0 ^
  "-DCMAKE_C_FLAGS=-DWIN32 -D_WINDOWS -DNO_GETENV /Gy /Gw" ^
  -DCMAKE_ASM_NASM_COMPILER=C:/nasm/nasm-3.02/nasm.exe
cmake --build build\<target> --config Release
```

| File | Platform (`-A`) | Toolset (`-T`) | Compiler |
|---|---|---|---|
| `x86/jpeg-static.lib` | `Win32` | `v142` | MSVC 14.29.30133 |
| `x64/jpeg-static.lib` | `x64` | `v142` | MSVC 14.29.30133 |
| `arm64/jpeg-static.lib` | `ARM64` | `v143` | MSVC 14.44 |

- `jpeg-static.lib` is the Release build: `/O2 /Ob2 /DNDEBUG` with the static C runtime (`/MT`).
- `/Gy /Gw` take the place of `-ffunction-sections -fdata-sections`. `/O2` already includes `/Gy`. A linker only drops
  the unused sections with `/OPT:REF`.
- `WITH_CRT_DLL` stays off, which is what selects the static C runtime.
- No whole program optimization (`/GL`), so the libraries are not tied to one compiler version, and no `/arch:AVX2`.
- The `jconfig.h` generated by these builds has the same content as `../includes/jconfig.h`.

Checks:

- No library references `getenv`, has TurboJPEG symbols or has the arithmetic coder.
- An encoder test with the x64 and the x86 library gives the same output as the libraries of the official
  libjpeg-turbo 3.2.1 installer, on Windows 11 and, for x86, on Windows 7.
- An x64 Release agent linked with the library ran as a service with a remote desktop session on Windows 11.
- The ARM64 library was built but never run.
